    03

    Delivery semantics

    Надійність означає роботу з невизначеністю

    AT-MOST-ONCE

    Нуль або один раз

    Повідомлення не повторюється, але може бути втрачено при failure. Підходить лише коли втрата допустима.

    AT-LEAST-ONCE

    Один або більше разів

    Broker повторює повідомлення без ack. Робота не губиться, але consumer мусить бути idempotent.

    RETRY

    Exponential backoff

    Повторюємо тимчасові помилки через дедалі більші інтервали та додаємо jitter.

    DEAD-LETTER QUEUE

    Ізоляція poison messages

    Після вичерпання спроб повідомлення переходить у DLQ для аналізу або replay.

    Duplicate message ≠ duplicate audit

    Consumer записує `jobId` у таблицю processed jobs в одній транзакції з результатом. Повтор із тим самим ID завершується без повторного side effect.

    01

    Strong vs eventual

    «Актуальні дані» — це вимога, а не властивість за замовчуванням

    STRONG CONSISTENCY

    Останній підтверджений запис видно одразу

    W: completed→R: completed

    Потрібно для унікальності, balance, state transitions та рішень, які не можна приймати на застарілих даних.

    Копії сходяться з часом

    Підходить для cache, search index, analytics і notification projection, якщо продукт пояснює проміжний стан.

    TTL

    Обмежує вік копії

    02

    Timeout · retry · circuit breaker

    Кожен remote call має обмежений failure budget

    TIMEOUT

    Не чекати безкінечно

    Deadline враховує весь request budget. Connection і operation timeouts мають бути коротшими за caller deadline.

    request deadline: 2s
    EXPONENTIAL BACKOFF

    Retry лише transient failure

    Обмеж кількість спроб, додай jitter та idempotency. Permanent validation error повторювати не можна.

    200ms → 400ms → 800ms ± jitter
    CIRCUIT BREAKER

    Зупинити каскад

    Після серії failures circuit відкривається, fast-fail або fallback захищає threads і dependency.

    closed → open → half-open
    Notification provider down→Audit продовжується→Outbox retry + status у UI

    Backup · disaster recovery · RPO · RTO

    Recovery має числові цілі та перевірений runbook

    RPO · RECOVERY POINT

    Скільки даних можна втратити?

    RPO 15 хвилин означає: після disaster відновлений state може відставати не більш ніж на 15 хвилин.

    continuous WAL + cross-region copy
    RTO · RECOVERY TIME

    Скільки може тривати outage?

    RTO 60 хвилин — budget від incident до відновленого critical journey, включно з detection і validation.

    detect → failover → verify ≤ 60m
    RESTORE TEST

    Backup без restore — припущення

    Регулярно відновлюй database та object metadata в ізольованому середовищі, перевіряй checksum і application invariants.

    quarterly recovery exercise
